# ProofPitch AI commercial pilot plan

## Target buyer and trigger

The initial buyer is a freelance web developer or small web agency that has identified a concrete public website issue for a prospective service business but needs a credible, organized way to turn that observation into a reviewable offer. The trigger is a discovery call, referral, or manual website review where the agency needs to show evidence without overstating business impact.

## Pilot output

The pilot output is one source-backed prospect package:

- A deterministic audit with live/demo provenance.
- An inspectable proof record tied to the audit.
- One bounded local landing-page concept.
- A manually edited quotation with currency, line items, deliverables, exclusions, and timeline.
- A saved proposal revision that can be printed and manually moved through the pipeline.

The pilot does not send messages, collect payment, deploy changes, or claim conversion lift.

## Pricing assumptions

The quotation is intentionally operator-supplied. A pilot operator can enter a hypothesis such as:

| Assumption | Example | Status |
| --- | ---: | --- |
| Discovery and audit preparation | 1.0 hour | Estimate to be tested |
| Concept and review | 2.0 hours | Estimate to be tested |
| Delivery labour rate | 75 USD/hour | Editable assumption |
| Variable tooling cost | 0 USD in the local MVP | Placeholder, not a payment record |

Contribution model: **accepted fee − estimated delivery labour − variable costs**. The application must never present an entered quotation as accepted revenue or a simulated payment.

## Measurement plan

For each pilot package, record manually:

1. Time from audit start to first proposal draft.
2. Time from first draft to saved quotation revision.
3. Whether the agency can explain the evidence and scope without reopening the source site.
4. Reviewer rating of proposal usefulness on a 1–5 scale.
5. Which finding, concept, or quotation field was edited before sharing.

Use comparable tasks and report the number of packages. Do not claim time savings until there is a baseline and observed sample.

## Future validation funnel

Track these as separate events, never as one revenue number:

- Proposals prepared.
- Meetings booked.
- Proposals accepted.
- Work started.
- Payments actually received.

Demo fixtures and test records must remain excluded from the funnel. The local MVP stores proposal and pipeline state, but it does not record payments or send outreach.

## Interview and pilot feedback script

- What evidence did you need to make the recommendation credible?
- Was the local concept understandable without showing a live redesign?
- Which quotation field was difficult to complete?
- Did the proposal clearly separate observed facts from suggested scope?
- What would make you reuse this workflow on the next prospect?

Revise the offer if users cannot identify the observed source, if pricing is routinely invented rather than entered, or if the concept does not clarify the proposed work.
